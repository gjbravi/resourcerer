# Concepts

> Clusters, workloads, components, schedules, and other Orion terminology


## Cluster {#cluster}

In the context of Orion, a _cluster_ is a Kubernetes cluster where the workloads you want to optimize are deployed and on which you have installed the [Orion Agent](#agent) using the cluster name (`clusterName`) that you provide.

A cluster can have only one Agent installed. In the context of Orion, "adding a cluster" and "installing the Agent" have equivalent meaning and are used interchangeably.

For installation instructions, see [Install Orion on a cluster][install] in the Install topic.

## Workloads {#workloads}

A _workload_ is a component that runs inside one or more Kubernetes pods. In the context of Orion, a workload is a named Workload resource from a namespace in a cluster. Orion observes the resource utilization of workloads in order to produce *[recommendations](#recommendations)*—sets of optimal values for requests and limits—for them.

Orion can produce recommendations for the following Workload types: DaemonSet, Deployment, ReplicaSet, ReplicationController, and StatefulSet.

## Custom workloads {#custom-workloads}

A _custom workload_ is a workload type defined by a Custom Resource Definition (CRD). Orion can be configured to recognize CRDs as workloads — including custom workload CRDs, operator-owned workloads, and in-house platform operators — by declaring them in the `workloadResourceKinds` Helm parameter. Orion then generates request and limit recommendations for identified custom workloads the same as for standard workloads.

Related information:
- [Custom workload kinds][custom-workloads]

## Orion Agent {#agent}

The Orion Agent is a Kubernetes controller that watches workloads and configuration across the cluster and reports on them to the Orion platform. The **Orion Forwarder** runs alongside the Agent and streams a limited set of resource-related metrics to the Orion platform.

The Agent discovers and gathers metrics for all DaemonSet, HPA, Pod, ReplicaSet, ReplicationController, and StatefulSet types across all namespaces on the cluster on which it's installed.

By default, Orion is installed in the `orion-system` namespace.

The Orion Agent leverages the Kubernetes **`view`** role, granting **read-only** permissions on all resources in the cluster.

Related information:
- [Orion architecture][arch]

## Orion Node Agent {#node-agent}

The Orion Node Agent is an optional DaemonSet that runs on GPU nodes and collects GPU metrics. It is disabled by default.

When enabled, it reports each container's GPU memory usage and GPU allocation, along with device-level activity for each GPU. The Forwarder scrapes the Node Agent and sends those metrics on with the rest.

The Node Agent's ClusterRole grants **read-only** permissions on pods and Dynamic Resource Allocation resource slices. It needs additional host access on the node to read GPU state.

Related information:
- [Node Agent configuration][node-agent-config]
- [GPU optimization][gpu]

## Orion Applier {#applier}

The Orion Applier is a Kubernetes controller that manages request and limit settings for each workload and applies the [recommendations](#recommendations) generated by Orion machine learning. The Applier uses the same Orion credentials file as the Agent and runs in the same namespace.

The Applier is installed by default and enables you to:

- **Deploy recommendations automatically** on a schedule of your choosing. This option enables you to skip manually reviewing the recommended settings and ensures your settings track closely to actual CPU and memory use.
- **Deploy recommendations on demand**. For example, you can apply a single recommendation in any environment as you experiment with recommendations or if you need to quickly deploy a recommendation outside of a schedule.

The Applier applies recommendations using a combination of [In-place Pod Resizing](https://kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/), [Server-Side Apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/) patches, and [Mutating Admission Webhooks](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/#mutatingadmissionwebhook). Use the [_apply method_][apply-method] configuration option to control how recommendations are applied for individual workloads.

The Applier leverages the Kubernetes **`edit`** role, enabling it to **update and patch** all optimizable workloads (and HPA, if enabled). You can grant additional permissions by specifying additional RBAC in the Helm install command.

Related information:
- [Applier configuration][applier-config]
- [Additional RBAC permission][applier-rbac]

## Schedule {#schedule}

The _schedule_ defines how frequently Orion generates (and optionally deploys) a [recommendation](#recommendations) for a workload.

By default, a new recommendation is generated once daily (`@daily`) for a workload, which is considered a best practice.

With a once-daily schedule, Orion can account for daily traffic patterns. For example, recommendations generated on a Monday might differ from those generated on a Saturday because resource usage patterns often differ between weekdays and weekends.

If [auto-deploy] is enabled, recommendations are deployed as soon as they're generated.

To ensure that numerous workloads aren't restarted simultaneously, Orion staggers the generation and deployment of recommendations throughout the schedule period (when the schedule is an ISO 8601 Duration string or equivalent schedule macro). For details, see the Schedule setting topic linked below.

Learn about how the [_validity period_](#validity-period) affects the lifetime and request values of recommendations.

Learn about how a workload's [_learning period_](#learning-period) determines how soon recommendations can be auto-deployed after workload discovery.

Related information:
- [Schedule][schedule-setting] setting

## Validity period {#validity-period}

<div class="alert alert-info" role="alert"><div class="h4 alert-heading" role="heading">Tip</div>


You usually don't need to change the validity period. Consider extending it only if you want recommendations to remain valid beyond the schedule interval.
</div>


The _validity period_ defines how long a [recommendation](#recommendations) remains valid after generation.

By default, the validity period is based on the recommendation [schedule](#schedule). For example, when recommendations are generated daily, the validity period for each recommendation is automatically set to ≥ 1 day.

The validity period can also be configured independently from the schedule, extending recommendation lifetime while recommendations continue to be generated according to the schedule.

For example, with the schedule set to `@daily` and the validity period set to `P7D`:
- Recommendations are generated daily
- Each recommendation remains valid for 7 days

New recommendations reflect recent usage patterns, while existing recommendations remain valid for the duration of the validity period. This configuration can be useful for teams that generate recommendations frequently but may not deploy them immediately, such as those using manual deployment processes.

In contrast, a weekly schedule with a 7-day validity period generates only one recommendation per week, making it less responsive to day-to-day traffic changes.

The validity period also affects how aggressively Orion adjusts resource requests. Longer validity periods generally result in more conservative recommendations to keep workloads stable throughout the validity period.

Setting a longer validity period can therefore result in lower savings, because Orion must account for a wider range of usage patterns.

Key points:
- The default validity period is sufficient for most cases.
- A recommendation shouldn't be used beyond its validity period.
- Validity period must be greater than the recommendation schedule frequency.

Related information:
- [Validity period][validity-period] setting

## Learning period {#learning-period}

The _learning period_ acts as an automation gate, defining the number of days that must pass after discovering a workload before the Applier is permitted to deploy recommendations automatically.

Because CPU and memory usage patterns can vary from day to day, it can take up to 7 days to collect a robust set of metrics and generate well-informed recommendations. For this reason, the default learning period duration is 7 days (`P7D`).

During the learning period, Orion collects metrics on the workload and generates [_preliminary recommendations_][preliminary-recs]. You can review and apply these recommendations on demand (by clicking **Apply Now** on the workload details page), but they can't be auto-deployed, even if auto-deploy is enabled.

Preliminary recommendations are generated hourly for the first 23 hours, then as defined by the [schedule](#schedule)—by default, once daily (`@daily`)—for the remainder of the learning period and beyond. If auto-deploy is enabled, recommendations are deployed immediately following generation.

See [Recommendations][recommendations] for details about how the schedule and learning period determine how frequently recommendations are generated and how soon they can be auto-deployed.

Related information:
- [Learning period][learning-period] setting

### Auto-deployment sooner than 7 days {#learning-period-shorter}

If you want to automatically deploy recommendations sooner—for example, for short-running workloads, branch-based deploys, or other ephemeral environments—you can shorten the learning period. 

Otherwise, for typical workloads, be aware that metrics collection might not be complete. Consider reviewing and manually applying the preliminary recommendations instead.

Shortening the learning period changes how soon recommendations can be auto-deployed. See the [Recommendations][recommendations] section for [schedule and learning period examples][preliminary-examples].

Related information: 
- [Auto-deploy][auto-deploy] setting

## Recommendations {#recommendations}

A Orion _recommendation_ is the set of resource requests and limits that the machine learning algorithm has determined to be optimal for a workload, based on historical utilization observations.

Orion can produce recommendations for the following items:
- Kubernetes Workload types: DaemonSet, Deployment, ReplicaSet, ReplicationController, and StatefulSet
- [Custom workload](#custom-workloads) types defined by CRDs
- HPA, when enabled and scales on at least one resource metric (see [HPA recommendations][hpa-recommendations])
